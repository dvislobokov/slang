# Отладчик

Цель: отладка уровня Delve/dlv и VS Code-интеграции, но быстрее там, где
Delve интерпретирует: условные точки останова, вычисление выражений,
перечисление задач. Преимущество Slang — компилятор на LLVM (DWARF
бесплатно) и компилятор как библиотека (отладчик компилирует условия и
выражения в нативный код).

## Этап 1: DWARF + lldb/gdb + DAP

- Кодогенерация пишет DWARF 5 через LLVM `DIBuilder`: compile unit на файл,
  функции (включая мономорфизированные generics с читаемыми именами
  `Max<int>`), параметры и локальные переменные с местоположениями, строки,
  инлайн; типы: примитивы, структуры с полями, указатели, `weak`, срезы,
  строки, map, кортежи, enum (простые и с данными как tagged union),
  интерфейсы (fat pointer), `T!` (как union {value, error}), `Task<T>`,
  замыкания, фреймы корутин (локальные переменные видны после `await`).
- Включено по умолчанию в debug-сборке; `slang build --release -g` для
  release с отладочной информацией; `--strip` убирает.
- **Форматтеры типов**: `tools/lldb/slang_formatters.py` (string → текст,
  slice → массив, map → пары, `T!` → значение или `error: ...`, enum →
  имя варианта с полями, interface → динамический тип и значение, Task →
  состояние) и `tools/gdb/slang_printers.py`. Подключаются автоматически
  через `slang debug --lldb` или вручную.
- **DAP**: `lldb-dap` с форматтерами; клиент в `editors/vscode`
  (конфигурация `type: "slang"`, запуск `slang build` перед отладкой,
  `program`/`args`/`env`/`cwd`, attach по pid). Работают точки останова,
  условия (вычисляются lldb — медленно, см. этап 2), шаги, стек,
  переменные, watch, REPL-выражения в синтаксисе lldb.
- Паника останавливает отладчик в месте паники (точка на `slang_panic`).

## Этап 2: `slang debug` — отладочный агент внутри процесса (без ptrace)

Основной отладчик — не внешний процесс, а **агент внутри отлаживаемой
программы**, как в Java (JDWP), .NET, Python и JavaScript. Debug-сборка
линкует агент (`runtime/src/debug/`), который слушает DAP по сокету
(`SLANG_DEBUG=:2345` или `slang debug run app.sl`); редактор подключается
напрямую. Внешний ptrace-отладчик не нужен.

### Механика

- **Точки останова и шаги**: компилятор в debug-сборке ставит на границе
  каждого оператора хук `if (slang_dbg_on) slang_dbg_stmt(id)` — один
  предсказуемый branch, при выключенном агенте стоимость около нуля.
  Агент держит таблицу активных точек; `next`/`step`/`step out` — те же
  хуки плюс глубина стека и id задачи, поэтому шаги `await`-aware по
  построению (следующая строка *в этой задаче*).
- **Переменные и стек**: агент читает DWARF своего бинарника (встроенный
  парсер на C/Rust) и память своего процесса обычными указателями;
  раскрутка по frame pointers (включены всегда).
- **Условия, логпоинты, выражения**: компилируются компилятором Slang
  (как библиотека в dev-сборке или через сокет к `slang`) против типов
  DWARF и вызываются как обычные функции в том же процессе. Ноль
  переключений контекста — главный источник скорости относительно Delve.
- **Задачи**: прямой доступ к списку задач планировщика; остановка одной
  задачи при работе остальных или заморозка всех; стек и точка `await`
  каждой задачи.
- **Паники и ошибки**: перехват в `slang_panic` и в местах создания
  ошибок (`break on error NotFound`) до раскрутки.
- **Память**: счётчик ссылок, владельцы, циклы — через рантайм.
- **Горячая замена функций** в dev-сборке тем же агентом.

### Чем быстрее Delve

| Delve | `slang debug` |
|---|---|
| Условная точка: остановка через ptrace на каждом попадании, условие вычисляет отладчик | Условие — скомпилированная функция в процессе; остановка только когда истинно |
| Выражения: интерпретатор подмножества Go | Полный язык, компилируется и выполняется в процессе |
| Логпоинты через остановку | Внедрённый код пишет в канал агента без остановки |
| Горутины: чтение структур рантайма через ptrace, секунды | Список задач в памяти агента, миллисекунды |
| Шаг через канал уводит в планировщик | Шаги по id задачи |
| Каждая операция — syscalls ptrace и переключения контекста | Всё в одном процессе |

### Что даёт отказ от ptrace

Переносимость без усилий: Linux, macOS без entitlements и подписи,
Windows, wasm в браузере, контейнеры без `CAP_SYS_PTRACE`; удалённая
отладка из коробки (сокет); один код агента для всех платформ; отладка в
проде по флагу без перезапуска.

### Чего агент не покрывает — и чем это закрыто

Подключение к процессу без агента, зависший агент, крэши, core-dumps —
внешний режим на базе lldb (этап 1): `slang debug core`, `attach --lldb`,
посмертный анализ с теми же форматтерами.

### Архитектура

```
editors (VS Code, IDEA) ──DAP/сокет──▶ агент в процессе (runtime/src/debug/)
                                       ├─ hooks: таблица точек, шаги по задаче
                                       ├─ dwarf: типы, локации (свой парсер)
                                       ├─ expr: компилятор Slang → код → вызов
                                       ├─ tasks: планировщик напрямую
                                       └─ cli: `slang debug` — тонкий клиент
```

## Этапы

1. DWARF в кодогенерации (все типы, локальные переменные, корутины),
   форматтеры lldb/gdb, `lldb-dap` в VS Code, тесты: скрипты lldb,
   проверяющие значения на точках останова в examples/.
2. In-process агент: хуки операторов в кодогенерации, таблица точек,
   шаги, стек и переменные по DWARF, DAP по сокету, тонкий клиент
   `slang debug`; замена `lldb-dap` в VS Code.
3. Компилируемые условия и выражения, логпоинты, список задач и шаги по
   задаче, остановка на паниках и ошибках.
4. Память и ошибки как объекты отладки, горячая замена, remote в проде.
5. Внешний режим (lldb) для крэшей и core-dumps; wasm.
