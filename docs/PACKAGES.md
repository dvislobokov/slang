# Менеджер пакетов Slang

Собственный менеджер пакетов, встроенный в CLI `slang`. Берёт у Go
воспроизводимость (minimal version selection, журнал контрольных сумм),
у Cargo — манифест, lock-файл, реестр, features и workspace, и добавляет
то, что возможно только при своём компиляторе: кэш собранных пакетов и
анализ capabilities.

## Принципы

1. **Воспроизводимость.** Minimal Version Selection: из всех версий,
   удовлетворяющих ограничениям, выбирается минимальная. Новый релиз
   зависимости ничего не меняет, пока не выполнен `slang update`.
2. **Одна мажорная версия пакета в графе.** Конфликт мажорных версий —
   ошибка с объяснением, кто кого требует. Путь импорта не содержит версию.
3. **Имя пакета = корневое пространство имён.** `slang add http-router`
   даёт `import router` (имя namespace задаёт пакет в манифесте, реестр
   гарантирует уникальность).
4. **Целостность.** Хэш каждого пакета в `slang.lock`; реестр ведёт
   публичный append-only журнал контрольных сумм, клиент сверяет с ним.
5. **Реестр не обязателен.** Зависимость может быть из git или локального
   пути. Приватный реестр — статическая директория с индексом, раздаётся
   любым HTTP-сервером (sparse-индекс, как у Cargo).

## Манифест: `slang.toml`, `slang.json` или `slang.yaml`

Формат манифеста выбирает автор проекта, по имени файла. Все три формата
описывают одну и ту же схему; `slang init --format json|yaml|toml` создаёт
нужный, `slang manifest convert yaml` переводит между ними. В корне проекта
допускается только один манифест. Схема публикуется как JSON Schema
(`slang manifest schema`), поэтому редакторы дают автодополнение и проверку
во всех трёх форматах.

```toml
[package]
name = "shop"
version = "0.3.1"
namespace = "shop"          # корневое пространство имён пакета
entry = "src/main.sl"       # точка входа для бинарника (опционально)
license = "MIT"
description = "Example service"

[dependencies]
http-router = "^1.2"
json = "~2.0.4"
crypto-extra = { version = ">=0.5, <1", features = ["argon2"] }
internal-lib = { path = "../internal-lib" }
experimental = { git = "https://github.com/org/exp", tag = "v0.4.0" }

[dev-dependencies]
testkit = "^1"

[features]
default = ["tls"]
tls = ["http-router/tls"]
metrics = []

[workspace]
members = ["services/*", "libs/*"]
```

Тот же манифест в YAML:

```yaml
package:
  name: shop
  version: 0.3.1
  namespace: shop
dependencies:
  http-router: ^1.2
  json: ~2.0.4
  crypto-extra: { version: ">=0.5, <1", features: [argon2] }
  internal-lib: { path: ../internal-lib }
dev-dependencies:
  testkit: ^1
features:
  default: [tls]
  tls: [http-router/tls]
```

- Ограничения версий: `^1.2` (>=1.2, <2), `~1.2.3` (>=1.2.3, <1.3),
  `>=1, <2`, `=1.4.0`.
- `features` — условная компиляция через `@cfg(feature: "tls")` на
  объявлениях.

## Lock-файл `slang.lock`

Всегда один формат независимо от формата манифеста: детерминированный
YAML с отсортированными ключами (читается человеком, хорошо сливается в
git). Генерируется автоматически, коммитится в репозиторий. Содержит точную
версию, источник и хэш каждого пакета в графе, включая транзитивные.
Читается не только сборкой, но и LSP (навигация внутри зависимостей) и
`slang doc`.

## Команды

| Команда | Действие |
|---|---|
| `slang init [name]` | создать `slang.toml` и `src/main.sl` |
| `slang add pkg[@constraint] [--dev] [--features a,b]` | добавить зависимость, обновить lock |
| `slang remove pkg` | удалить зависимость |
| `slang update [pkg]` | поднять версии в рамках ограничений |
| `slang build` / `run` / `test` | сами скачивают и собирают зависимости |
| `slang publish` | опубликовать в реестр (проверка манифеста, тестов, подписи) |
| `slang audit` | сверить граф с базой уязвимостей |
| `slang vendor` | скопировать все зависимости в `vendor/` |
| `slang install [--offline]` | привести `.slang/deps` в соответствие с lock-файлом |
| `slang store verify / prune / path` | проверить, очистить, показать хранилище |
| `slang manifest convert <fmt> / schema` | сменить формат манифеста, вывести JSON Schema |
| `slang tree` | показать граф зависимостей |
| `slang why pkg` | объяснить, кто требует пакет |

## Хранилище и кэш (модель pnpm)

Одно глобальное **контентно-адресуемое хранилище** `~/.slang/store/`:

- Каждый файл каждого пакета лежит там один раз, под именем своего хэша
  (`store/files/<sha256>`); версия пакета — это индекс «путь → хэш»
  (`store/packages/<name>/<version>/index.yaml`). Десять проектов с одной
  и той же зависимостью занимают место один раз.
- В проект пакеты не копируются. Каталог `.slang/deps/<name>@<version>/`
  заполняется **жёсткими ссылками** на файлы хранилища (на той же файловой
  системе), иначе reflink/копия. Установка — это создание ссылок, поэтому
  она занимает миллисекунды и не зависит от размера пакетов.
- Целостность: хэш каждого файла проверяется при добавлении в хранилище
  и при `slang store verify`. Повреждённый или подменённый файл
  обнаруживается, а не тихо компилируется.
- **Строгая изоляция зависимостей**: пакет видит только то, что объявил в
  своём манифесте. «Фантомные» зависимости невозможны: компилятор разрешает
  `import` только по графу из lock-файла.
- `slang install --offline` собирает из хранилища без сети; `slang store
  prune` удаляет версии, на которые не ссылается ни один проект;
  `slang store path` показывает расположение. Хранилище можно вынести на
  общий диск (`SLANG_STORE`) для CI.

**Кэш сборки** живёт рядом: `~/.slang/store/build/<pkg>/<hash>/`, где хэш
учитывает версию пакета, набор features, профиль, версию компилятора и
целевую платформу. Внутри — объектный файл и сериализованный HIR с
сигнатурами. Все проекты на машине переиспользуют его; после первой
сборки зависимости не перекомпилируются. Генерики мономорфизируются на
стороне использующего пакета по сериализованному HIR. Кэш сборки — просто
директория, его можно выгружать в CI-артефакт или удалённый кэш
(`SLANG_BUILD_CACHE=https://...`, как у sccache).

## Безопасность

- **Подпись релизов** ключом издателя; реестр проверяет при публикации,
  клиент — при скачивании.
- **Capabilities.** Стандартная библиотека помечает «опасные» точки:
  сеть (`std.net`), файлы (`std.fs`, `std.io` файловые функции), процессы
  (`std.process`, `std.os`), FFI/unsafe. Компилятор вычисляет, какие из них
  достижимы из пакета, и пишет в метаданные. `slang add` показывает:
  `http-router: network`, `left-pad: none`. Пакет, который внезапно
  начинает использовать процессы в новой версии, подсвечивается при
  `slang update`.
- **`slang audit`** — база уязвимостей в реестре, проверка по lock-файлу,
  в CI через `slang audit --deny`.
- Скрипты сборки в пакетах запрещены. Нет `build.rs` и post-install hooks,
  нечему выполняться при установке.

## Реестр

- Публичный реестр: индекс (sparse, HTTP), хранилище архивов, журнал
  контрольных сумм, документация для каждой версии (`slang doc` на
  сервере), поиск.
- Имена пакетов: `[a-z0-9-]`, уникальны. Пространства имён издателей
  (`org/pkg`) допускаются для приватных реестров.
- Зеркало: `SLANG_REGISTRY=https://mirror.internal` или в `slang.toml`
  секцией `[registries]`.
- Yanking версии (запрет для новых проектов, существующие lock-файлы
  продолжают работать).

## Чего не будет

- Нескольких версий одной мажорной ветки в одном бинарнике.
- Скриптов, выполняющихся при установке пакета.
- Версии в пути импорта (`pkg/v2`).
- Обязательной привязки пакета к git-хостингу.

## Этапы

1. ✅ **Готово.** Манифест (TOML/JSON/YAML, общая схема), `path`-зависимости, workspace, компиляция многопакетного
   проекта (нужно для разбиения стандартной библиотеки на пакеты).
   Что реализовано (`compiler/src/package/`, `compiler/src/build.rs`):
   - манифест `slang.toml` / `slang.json` / `slang.yaml` (ровно один в
     директории, иначе ошибка со списком), одна serde-модель;
     `slang manifest schema` (JSON Schema через `schemars`),
     `slang manifest convert <fmt>` (с проверкой round trip);
   - поиск проекта вверх от текущей директории; enclosing `[workspace]`,
     в котором директория перечислена как member, становится корнем;
     `slang build/run/check/test` без пути, `--workspace`, `-p name`;
     путь к файлу или к директории без манифеста — прежняя сборка без пакетов;
   - исходники `src/**/*.sl`; `entry` — бинарник, без `entry` — библиотека;
     `slang init [dir] [--format toml|json|yaml] [--lib]`;
   - граф `path`-зависимостей: дедупликация по каноническому пути, поиск
     циклов (`a -> b -> a`), проверка имён и features зависимостей;
   - корень пространства имён (`namespace`, по умолчанию имя с `-` → `_`) —
     один идентификатор, уникальный в графе; все файлы пакета объявляют
     `namespace <root>` или `<root>.<sub>`;
   - **строгая изоляция**: файл видит только `std`, свой пакет и прямые
     зависимости своего пакета — и в `import`, и в полном пути без импорта.
     Реализовано хуком `sema::ImportPolicy` (проверка первого сегмента
     пути); ошибка называет пакет, который надо добавить в `[dependencies]`,
     и через какую зависимость он доступен транзитивно;
   - каждый пакет компилируется в свой объектный файл
     `target/slang/<pkg>-<hash>.o` (хэш от IR пакета, флагов и компилятора;
     неизменённый пакет не перекомпилируется), затем всё линкуется;
     у каждой функции и глобала своя секция, `--release` линкует с
     `--gc-sections` и `-s`, `--static` — полностью статический бинарник.
   - Ограничения этапа: `dev-dependencies` разрешаются и попадают в lock,
     но видны только в `slang test`, который пока только проверяет типы;
     `features` проверяются, но `@cfg` ещё нет.
2. `slang.lock`, git-зависимости, MVS.
   - ✅ `slang.lock` для `path`-пакетов: детерминированный YAML
     (отсортированные пакеты и ключи), у каждого пакета `name`, `version`,
     `source: path:<путь от корня>`, `dependencies`, `checksum:
     sha256:...` по отсортированным исходникам. Перезаписывается при
     сборке, если граф, версии или исходники изменились; `--locked`
     превращает это в ошибку. Поле `source` (`graph::Source`) готово для
     `registry+...` и `git+...`.
   - Не сделано: git-зависимости, MVS, ограничения версий.
3. Контентно-адресуемое хранилище с жёсткими ссылками, кэш сборки.
   (Пока есть только локальный кэш объектов в `target/slang/`.)
4. Реестр: индекс, `publish`, `add` из реестра, журнал контрольных сумм.
5. Capabilities, `audit`, подписи.
